## 0. なぜこの3つを同時にやるか

ユーザー要望はそのまま以下:

> 武装やフレームなど色々各種類増やしてください
> 足がついた歩行型などもお願いします
> 高さなどももう少し自由度ある設計ができるようにお願いします

3つは独立に見えて**同じ一点**に集まる。今の機体は
**「床から 0.41〜0.53m の平たい板」以外になれない**。理由は3つ:

1. 車高は `DriveDef.radius` だけで決まる（`assemble.ts:291` が取り付け行を捨てて `y = radius` に固定）。
2. デッキの上に**物を積む概念が無い**。`PlacedPart` は面とセルだけを持ち、階層を持たない。
3. 垂直面の行は `groundClearance + v*CELL` で床から積むので、
   **胴体（0.07〜0.14m）より上の行は宙に浮いた板**でしかない。

だから「高さの自由度」は数値を大きくする話ではなく、**構造を足す話**になる。
そして脚は、その構造の中で**車高を大きく変えられる唯一の駆動**になる。

## 1. 脚駆動 `kind: "leg"`

### 1.1 何を作るか（設計判断）

**回転駆動の脚（rotary-driven leg）を作る。関節を持つ多リンク脚は作らない。**

理由:
- 既存の `DriveRuntime` は **剛体1・コライダー（1つ以上）・ジョイント1** で固定されている
  （`assemble.ts:28-46`）。多リンク脚はこの形に入らず、`damage.ts` の脱落処理、
  衝突グループ、スナップショットの全部を作り直すことになる。
- 多リンク脚は**姿勢制御器（バランサ）が要る**。それが無いと倒れる。
  4機×4脚×3関節を毎ステップ制御するのは、この 20試合ゲートが守っている
  `avgStepMs ≈ 0.4` の予算に入らない。
- 実在の歩行機械（RHex、ストランドビースト、Klann 機構）は
  **1本のクランクの回転を脚の運動に変える**。回転駆動は「手抜き」ではなく本来の工学。

したがって **脚 = 車軸から放射状に伸びる剛体の脚（2〜4本）**。
車輪と**物理の位相構造が同一**（剛体1・revolute 1・モータ速度1）なので、
`driver.ts` / `damage.ts` / `net/*` は**一行も変えずに動く**。

### 1.2 契約 L1〜L7

- **L1** `DriveDef.kind` に `"leg"` を追加する。`"wheel" | "track" | "leg"`。
- **L2** 脚のコライダーは `feet` 本の**カプセル**であり、**同一の剛体**に付く。
  第 k 本の角度は `2πk / feet`（+ 後述の位相バイアス）。
  **各カプセルの最遠点は車軸から厳密に `def.radius`**。
  ＝ 車輪と同じ「外形＝`def.radius`」契約に従う。接地面が `-radius` になるのはこれによる。
- **L3** 車軸は**シャーシローカル X**、中心は `(local.x, def.radius, local.z)`。
  ＝ 既存の C-DRIVE 契約をそのまま守る。**脚だけの例外を作らない。**
- **L4** **左右で位相をずらす**。`assemble` は脚の初期姿勢を
  `side < 0 ? 0 : π / feet` だけ回して生成する。これで接地が交互になり、
  跳ねる（hopping）のではなく**歩く**。位相は物理の初期姿勢であり、
  毎ステップ制御するものではない（＝制御器を持たない）。
- **L5** 脚は**接地が断続的**なので、`DRIVE_TRACTION_ASSIST` をそのまま掛けると
  「宙に浮いたまま滑る」。`DriveDef.tractionAssist?: number` を追加し、
  脚は **0.12 前後**（車輪の 0.35 に対して低い）を持つ。未指定なら従来の定数。
- **L6** 脚の性格（カタログ担当への envelope）:
  **最高速は車輪の 0.5〜0.7 倍**、**トルクは 1.4〜1.8 倍**、
  **`friction` は高め（1.4〜1.9）**、`mass` は同径の車輪より 1.2〜1.5 倍。
  つまり「遅いが押しが強く、段差に強い」。履帯との差は
  **履帯＝接地が連続で安定／脚＝接地が断続で不安定だが車高を稼げる**。
- **L7** 脚は `radius` を大きく取れる（0.18〜0.30）。これが
  「高さの自由度」の**駆動側の答え**になる。⚠ ただし `radius` を上げると
  車高が上がり重心も上がるので、§2 の安定度指標に効くこと。

### 1.3 描画（`render/procedural/leg.ts`）

**物理の脚と同じ本数・同じ角度・同じ最遠点**で描く。ここを外すと今回のセッションで
3回踏んだ「描画と物理で真実が2つある」に戻る。

- 1本の脚は **大腿（ハブ側の太いリンク）＋膝の関節ブロック＋脛（細く先細り）＋足パッド**。
  膝は**曲げて造形してよいが、足パッドの先端は必ず車軸から `def.radius`**。
- 足パッドはゴム（暗くマット）、リンクは金属。ハブは車輪のリムと同じ語彙を使う。
- `ProceduralDrive.applyPhase(phase)` は**ハブごと回す**（車輪と同じ）。
  リンクを別々に動かさない＝物理と一致する。
- 恒久ゲート `driveGeometrySelftest` の既存6項目
  （中心・最大半径・幅・接地平坦性・法線向き・有限値）に**脚も通す**。
  ⚠ 「接地走行部が水平」の項目は脚には適用しない（断続接地なので原理的に平坦でない）。
  代わりに **`feet` 本の足先が全て `radius` ±0.5mm** を検査する。

## 2. 高さの自由度

### 2.1 何が足りないか

デッキの上に**段を作れない**。これを足す。

### 2.2 契約 H1〜H8

- **H1** `PlacedPart` に **`level?: number`**（既定 0）を追加する。
  `level` は `face === "deck"` のときだけ意味を持つ。他の面では 0 でなければならない。
- **H2** 新しい `PartType` **`riser`**（日本語ラベル「支柱」）を追加する。
  `RiserDef extends PartDefBase { category: "structure"; rise: number; }`
  `rise` は**この支柱が作る次の段までの高さ（m）**。0.10〜0.30 の範囲。
  ⚠ `category` に `"structure"` を新設する。既存の
  `chassis | drive | weapon | armor | utility` に**6つ目**を足す。
  `catalogSelftest` の roster 検査に `structure >= 3` を追加すること。
- **H3** `level = L` のデッキ面パーツの高さは
  ```
  y = groundClearance + chassis.height + Σ(k=0..L-1) riseAt(k) + part.height / 2
  ```
  `riseAt(k)` は**そのセルを支えている支柱の `rise`**。
  同一レベルの支柱は**すべて同じ `rise` でなければならない**（混在は H6 で弾く）。
- **H4** `level >= 1` のパーツは、**自分の占有セル全部**が
  `level - 1` の支柱の占有セルに**完全に含まれて**いなければならない。
  ＝ 宙に浮いた段は作れない。
- **H5** `ChassisDef` に **`maxLevels: number`** を追加する（既存6種は 1、新設の高床系は 2〜3）。
  `level > maxLevels` は不許可。
- **H6** `validateBuild` は H1・H2・H4・H5 違反を**日本語で**弾く。
  エラー文は必ず**パーツ名と段数**を含めること（保存済み機体が無効になり得るため）。
- **H7** `computeStats` は以下を返す:
  - `comHeight`: 全パーツ（シャーシ含む）の質量加重した重心の床からの高さ（m）
  - `trackWidth`: 左右の駆動の接地点の最大間隔（m）
  - `stability = trackWidth / (2 * comHeight)`。**1.0 未満は転びやすい**。
  ビルダーはこれを数値で表示する。**高くすると転びやすくなる**——
  これが「高さの自由度」を選択たらしめる代償であり、隠してはならない。
- **H8** 物理側は、支柱を**シャーシ剛体に固定したコライダー**として作る
  （新しい剛体を作らない）。段の上のパーツは**従来どおり**それぞれの剛体になる。
  質量と重心は Rapier が自動で合成するので、H7 の数値と物理は自然に一致する。

### 2.3 垂直面の行ピッチ（既存の歪みの扱い）

現状、左右／前後面の行は `groundClearance + v*CELL` で床から 0.12m 刻みに積み上がり、
胴体（0.07〜0.14m）より上は**支えの無い板**になっている。
**これは今回は変更しない。** 理由:
- 現行8プリセットの垂直面パーツは全て 0 行目にあり、破綻が見えていない。
- 行ピッチを胴体高に合わせて縮めると**既存の機体が全部低くなる**——
  ユーザーの要望と逆方向になる。

代わりに **H2 の支柱が「上に積む」正しい道**になる。垂直面は「側面に貼る」ためのものとし、
`heightCells` は**側面グリッドの行数**という本来の意味に留める。
⚠ 将来この歪みを直すときは、**支柱が既に存在すること**を前提に、
垂直面の行を胴体内に収める方向で直すこと。

## 6. 実装着手時に判明した補正（発注者が追記・2026-07-26）

契約を書いた時点では見えていなかった点。**以下が §1〜§5 に優先する。**

### 6.1 ⚠ `partLocalPosition` は段の高さを計算できない（H3 の穴）

`partLocalPosition(chassis, part, cell, rot, face)` は**その1パーツしか見ない**。
一方 H3 の `Σ riseAt(k)` は**機体に積まれた支柱**に依存する。
ここで描画側だけ別の式を書くと、**横付けタイヤ（5cm上・7cm外）とベルト裏返りを生んだのと同じ構造**になる。

したがって:

- **A1** `partLocalPosition` に**第6引数 `levelRise: number = 0`** を足す。
  意味は「この段の基準面が、デッキ面からさらに何m上か」。`deck` 面以外では常に 0。
  ```
  case "deck": y = groundClearance + chassis.height + levelRise + part.height / 2
  ```
- **A2** 新しい輸出 `levelRises(spec, catalog, chassis): number[]` を `build.ts` に置く。
  `[0, rise_0, rise_0 + rise_1, ...]` を返す（添字＝`level`）。
  **`assemble.ts` と `render/mounting.ts` は必ずこの関数の戻り値を使う。**
  どちらかが自前で足し算を書いたらレビューで差し戻す。
- **A3** ⭐ **`RiserDef.height` は `rise` と厳密に等しくなければならない。**
  そうすれば支柱自身も一般式 `y = base(level) + height/2` に乗り、天面が
  ちょうど次の段の基準面になる。`catalogSelftest` で `Math.abs(height - rise) < 1e-9` を検査する。
  高さと `rise` が食い違う支柱は**カタログの誤り**であってコードで吸収しない。

### 6.2 ⚠ 占有セルのキーに段が入っていない

`build.ts` の重複判定は `${face}:${i},${j}`。このままだと
**1段目と2段目の同じセルが「重なっている」と誤判定**され、多段が原理的に組めない。
→ **`${face}:${level}:${i},${j}` に変える。** `level` 既定 0 なので既存機体のキーは変わらない。

### 6.3 支柱は「6つ目のカテゴリ」だが分岐は少ない

`PartCategory` に `"structure"` を足すと 86 件のコンパイルエラーが出る（実測）。
内訳は `assemble.ts` 25 ／ `catalog.ts` 12（`maxLevels` 未指定の12フレーム）／
`BuilderPanel.tsx` 6 ／ `build.ts` 1 ＋ `RiserDef` に無いプロパティの参照。
**これは想定どおりで、型が実装箇所を漏れなく指している。** 握り潰さずに全部直すこと。
支柱の物理は **`category === "armor"` と同じ固定コライダー経路**に乗せる（H8）。

### 6.4 脚のカプセル配置（L2 の具体化）

車軸はシャーシローカル X。第 k 本の角度 `θ_k = 2πk/feet + bias` は **YZ 平面内**。
カプセル（Rapier では局所 Y 軸方向）を θ_k に向けるので、
- 姿勢 = X 軸まわり θ_k の回転 ＝ `(sin(θ_k/2), 0, 0, cos(θ_k/2))`
- 中心 = `(0, cos θ_k, sin θ_k) * d`、ただし **`d = radius − halfHeight − capsuleRadius`**

これで最遠点がちょうど `radius`。**この式以外で足先を出さないこと。**
位相バイアスは L4 のとおり `side < 0 ? 0 : π / feet`（左右で半歩ずらす）。

### 6.5 既存12フレームの `maxLevels`

既存フレームは**全て `maxLevels: 1`**（＝多段不可）にする。多段は新設フレームの売りにする。
これは「既存パーツの数値を変えない」(P1) に**抵触しない**——新フィールドの初期値だから。

## 7. 実装後の訂正（発注者が追記・2026-07-26）

敵対的レビューで反証を生き延びた指摘に基づく。**§7 が §1〜§6 に優先する。**

### 7.1 ⚠ L7 は書き過ぎだった — 脚は「デッキの高さ」を与えない

L7 は「脚は `radius` を大きく取れる＝高さの自由度の駆動側の答え」と書いたが、**成立しない**。
L3（車軸は `radius`）と併せると、星形の脚が保証する支持半径は**内接円**であって先端ではないので、
足と足の間で車軸が沈む。実測（`LEG_SPOKE_RADIUS_FRAC = 0.17` のとき）:

| 脚 | feet | radius | 内接 | 沈み込み | 腹をつくフレーム |
|---|---|---|---|---|---|
| leg-scout | 4 | 0.180 | 0.1362 | 0.0438 | 5/15 |
| leg-strider | 3 | 0.220 | 0.1287 | **0.0913** | **15/15** |
| leg-crab | 4 | 0.200 | 0.1514 | 0.0486 | 7/15 |
| leg-hauler | 4 | 0.260 | 0.1968 | **0.0632** | **15/15** |
| leg-stilt | 3 | 0.300 | 0.1755 | **0.1245** | **15/15** |

⭐ これは既存設計の潜在的な性質も暴いた: **車高は一度もタイヤ半径に依存していなかった。**
`assemble.ts` は車軸を `y = radius`、ハルを `y = groundClearance` に置くので、
0.30m のタイヤでも 0.08m のタイヤでもハルの高さは同じ。車輪では見えず、脚で致命的になった。

**訂正**: 脚が与えるのは**腹をこすらない地上高**であり、**デッキの高さを与えるのは支柱（§2）**である。

### 7.2 ハルの持ち上げ（新契約 L8）

- **L8** `build.ts` の `driveSupportRadius(def)` / `driveSinkDepth(def)` / `hullLift(spec, catalog)` が
  **唯一の出典**。車輪・履帯は 0、脚は `radius − ((radius−r_c)·cos(π/feet) + r_c)`。
  `assemble.ts` のハルのコライダーと全パーツ、`render/mounting.ts` の `BotMountGeometry`、
  `computeStats` の重心が**全部そこから読む**。自前で足し算した時点でレビューで差し戻す。
- 余裕 `LEG_HULL_MARGIN = 1.7`。静的な沈み込みだけでは足りない（歩行中のピッチングでハル隅が沈む）。
  実測: margin 1.0 で leg-walker のハル接地 24.2% / 1.7 で 0.8%。

### 7.3 ⚠ 位相は物理由来でなければならない（新契約 L9）

- **L9** 駆動の回転位相は**シムの剛体から取り**、`BotState.drivePhases` → `BotSnap.wp`（駆動ごとに1つ）
  で運ぶ。`PROTOCOL_VERSION = 5`。
  描画がシャーシの移動距離から積分し直すのは**禁止**（フォールバックのみ許す）。
  修正前の実測: 描かれる足先と物理の足先の高さ差 **最悪 108.5mm**（3本脚の理論最大 110mm にほぼ到達）。
  車輪は回転体なので位相がずれても見た目が同じ＝この欠陥は**脚を入れるまで見えなかった**。
- ⚠ **`wp` は累積角のまま送る。(−π, π] に折り畳んではならない。**
  20Hz では1スナップショットで最大 18 rad 進むので、折り畳むと 18 rad と 18−6·2π が区別できず
  補間が別の運動を再構成する。節約は実測 144 B しかない。
- ⚠ `arenaScene` の `forward` は**シャーシ +Z ＝ 後ろ**（前方の唯一の出典 `sim/heading.ts` は −Z を返す）。
  距離積分フォールバックは `+=` が正しい。変数名を `chassisBack` / `backwardDistance` に改名済み。

### 7.4 信頼できない機体データが資源を決めてはならない

- **`MAX_BUILD_LEVEL = 8`**: `levelRises` は段ごとに配列要素を作り、ホストは**検証前の**ゲストの
  機体でこれを呼ぶ。無制限だと `level: 1e9` で約8GB・65秒＝部屋が落ちる。
- **`MAX_DRIVES = 12`**: `wp` は駆動ごとに1つ。`chassis-fortress` は幾何学的に **231基**の
  1セル車輪を載せられるので、上限が無いとゲストが部屋全体の帯域を決めてしまう。
- **`storage.ts` は `level` を保存する。** 落とすと段が潰れて重なり判定に引っかかり、
  保存した多段機が**読み込めなくなる**（平らになるのではなく無効になる）。

### 7.5 ゲートに対する要求（今回7件が「検査になっていなかった」）

- **被覆を主張すること。** 比較ループが `continue` するだけで件数を言わないゲートは、
  全件飛ばしても満点で通る（実際に G-HEIGHT [B1] と脚の描画検査がそうだった）。
- **交絡を排すこと。** 「支柱を1段足すと重心が上がる」は支柱自身の質量で通ってしまう。
  **質量同一で段だけが違う対**を作り、差が `partMass × rise ÷ totalMass` と一致することを要求する。
- **高さだけを比べないこと。** 一様な星の足先高さの集合は位相の符号反転に対して不変なので、
  高さ指標だけのゲートは**符号の誤りを認証してしまう**（実際に通った）。3次元の位置で比べる。
- **本番と同じ式でフォールバックを模すこと。** 符号が違えば、それは別物を測っている。
