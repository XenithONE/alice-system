## 1. アリーナ ―「アーチ状になった円」

### 決定：円周に沿ったアーケード（列柱＋アーチ）。**床プロファイルは触らない。**

床は既に湾曲した円（`rings.ts` の radius→height プロファイル）である。ユーザーの言う
「アーチ状の円」が床のことなら既にそうなっているので、求められているのは**周囲の構造物**と読む。

- 手続き生成。柱＋迫持ちアーチ＋冠壁を**型ごとに1 InstancedMesh**で置く。
- 予算：**+3 draw call まで**。現状 121 → 124 を上限とする。超えたら統合するか本数を減らす。
- 低スペック（`detail === "lite"`）：アーチを省き柱のみ、発光帯オフ。
- `crowdLod`（5体以上）：アーチを角柱シルエットに落とす。

### リムのせり出し（オーバーハング）は**今回入れない**

将来入れる場合の解だけ記録する。オーバーハングは `f(r)=h` では表せない（1半径に2高さ）。
床の関数を多値化してはならない — 5アリーナ全部と補間と selftest が壊れる。

```
床  : 従来どおり single-valued f(r) = h
リム: 媒介変数 s∈[0,1] の曲線として別サーフェス化
      r(s) = outRadius - overhang * s²
      h(s) = lipBase + lipRise * s
```

描画と Rapier が**同じ生成関数**（`rings.ts` に置く `buildLipShellMesh`）を読むこと。
描画だけ反らせる実装は `ringSurfaceSelftest`（誤差 2.78e-16）が即座に落とす。

## 2. スキル演出 ― 8つの「型」

### 型は `effects` から導出する。スキルごとの手書き表は作らない。

実データ49件に当てて検証済み：**未分類ゼロ**。

| 型 | 判定（先に一致した方を採る） | 件数 |
|---|---|---:|
| G 吸収 | `steal-spin` か `cooldown-shift` | 4 |
| H 再起 | `durability` かつ `cleanse` | 4 |
| C 衝撃輪 | `radial-damage` | 5 |
| E 盾 | `shield` か `phase` | 9 |
| B 軌道 | `reverse-orbit` か impulse `tangent` | 4 |
| A 突進 | impulse `toward-target` | 5 |
| D 錨 | impulse `toward-center` / `away-from-target`、または `physics-multiplier` | 9 |
| F 過駆動 | `spin`、最後に `stat-multiplier` | 9 |

⭐ `tangent` を B に回すこと。諮問時の記述では漏れており、F や D に流れていた。

### 見た目（形・色・時間）

| 型 | 形 | 色 | 時間 |
|---|---|---|---|
| A 突進 | 自機→標的の鋭い錐形ストリーク＋接触点の火花 | シアン〜白 | 0.25–0.4s |
| B 軌道 | 独楽周囲を掃く接線アーク（1/4〜1/2円） | マゼンタ | 0.35s |
| C 衝撃輪 | 水平の拡大リング（半径＝イベントの radius） | 琥珀 | 0.5s 減衰 |
| D 錨 | 足元の下向き柱＋床の暗い波紋 | 鋼灰 | 最大1s＋薄い残像 |
| E 盾 | 胴を包む半透明ドーム | 水色 | duration 中 常駐（低opacity） |
| F 過駆動 | 既存 energy-aura を縦に伸ばし回転トレイルを太く | 金 | 0.2s＋残光1s |
| G 吸収 | 敵→自分の細い粒子ストリーム | 紫 | 0.6s |
| H 再起 | 上向き微粒子＋パルス輪 | 緑 | 0.8s |

`impact` は既存の汎用バーストを残し `power` でスケール。**攻撃＝白熱／スキル＝型色**で色空間を分ける。
回復（H）に暖色を使わない — 攻撃と混線する。

### 「わかりやすく」と「派手に」の両立 ⭐

派手にすると読めなくなる。**階層で解く。**

1. **第1層（必須・可読）**：型のシルエット。1色。0.3秒で読める。
2. **第2層（装飾）**：二次粒子・グロー・床デカール。`lite` では全カット。
3. **同フレーム多重時の優先度**：`knockout > shockwave > C > A/B > impact`。上位以外を間引く。
4. **派手さの予算を型ごとに固定**（例：C＝リング1＋粒子12、A＝ストリーク1＋粒子8）。全部を同時に最大輝度にしない。
5. 画面中央にテキストを出さない — ネット遅延で嘘になる。

## 3. イベント配線 ― 同じ事実を二度書かない

### 現状の欠陥（実測）

`SimEvent`（sim側・5種の判別共用体）と `BattleEventVisual`（描画側・`type: string` の緩い別型）が
**同じ事実を二重に手書き**している。`App.tsx:1226` の `eventToVisual` が橋渡ししているが：

- `shockwave` と `sudden-death` は変換されるのに `processEvents` の分岐に無く、**画面に何も出ない**
- `skillId` は `SimEvent` にあるのに `BattleEventVisual` に**載せずに捨てている**

（`knockout` は `reason` を見て `ringout`/`destroy` に変換され、描画されている。ここは正常。）

### 決定

- `BattleEventVisual` を `SimEvent` から**導出する**。手書きの第二の型を残さない。
- 取りこぼしを塞ぐ：`shockwave` = 型C の強化版（`radius` でリング拡大・seat色の縁）、
  `sudden-death` = アリーナ全体演出（リム emissive↑・フォグ密度↑・カメラ微振動、粒子は最小）。
- `skillId` を通し込む。**通信量の増加はゼロ**（既にプロトコルが運び検証している）。

## 4. コンボ ― 明示有向ペア12件

### 決定：タグ方式ではなく**明示ペア**。

49×49 の表は書かない。12件を人が選んで意図を持たせる。タグ方式は規模には強いが、
「どの組が光るのか」がプレイヤーにもオーサリング側にも読めなくなる。

```ts
interface ComboDef {
  readonly id: string;
  readonly opener: SkillId;     // 先に撃つ
  readonly finisher: SkillId;   // 窓の内に撃つ
  readonly withinTicks: number; // 30–180
  readonly effects: readonly SkillEffectDef[]; // 最大3
  readonly cue: FxFamily;
}
```

- **窓の状態はホスト内部**に持つ。20Hz snapshot には載せない → **定常増分0バイト**。
- 成立時だけ低頻度の `combo` イベントを送る。
- 同一スロットに積まれた A+B では成立させない（別入力を要求する）。
- opener / finisher の次数は各2以下 — 1本のスキルが多数のコンボの起点になるのを防ぐ。

## 5. 新規コンテンツ

- 新アクティブ **8**、新パッシブ **8**（既存98は改名も削除もしない）
- 新 effect kind は **2つだけ**：`target-multiplier` と `delayed-radial`
  - `cooldown-shift` は kind を増やさず**対象指定を拡張**する
- ⭐ 語彙を増やすほどホストの解釈コードとゲートが増える。**元が取れる最小限に留める。**

## 6. シナジーを「見える」ものにする

既存33件の数値倍率は**そのまま残す**（改名・再解釈しない）。その上に：

- lineage は最高段階**1件だけ**に proc を付ける
- role-pair は **featured 1件だけ**（構成数最大、同数なら id 昇順）に proc を付ける
- proc の cooldown は最低5秒

⭐ 33件すべてに proc を付けると画面ノイズとビルド差が急増する。
常時トレイル／色調は開始 payload の build からクライアントが導出 → **snapshot 増分0バイト**。

## 7. 動きの質感 ― シミュレーションに触れない

ホスト権威なので `dt` を止めるヒットストップ／スローは**禁止**。描画層のみ：

- カメラ：FOVの短いパンチ（40ms）、`impact.power` に比例した小さなシェイク（酔い対策に上限）、サドンデスで yaw 1.3倍
- 独楽：被弾時に**見た目だけ**2–4cm 押し出して80msで戻す（`target` は sim のまま、`root.position` にオフセット層）
- KO：即消しでなく0.35秒の転倒＋フェード
- アリーナ：衝突点の床デカール（Additive・0.3s・InstancedMesh 16個プール）
- 粒子：型で速度を拘束（A＝双方向コーン、C＝水平円盤、impact＝半球）
- `reducedMotion`：全オフ

## 8. UI ― ゲームは別世界、入口だけ地続き

`vortex.css` は既に独立トークン（`--vc-cyan` 等）を持つ。サイトの琥珀金を押し込むと
**戦闘のチームカラー（シアン／赤）と衝突する**。共有するのは Barlow Condensed・暗い背景・戻り導線だけ。

対戦中の情報優先度：
1. 自分のHP/SPIN、スキルの状態（ready / CD / 使用不可の理由）、残り人数
2. 勝敗に直結する状態（場外寸前・サドンデス段階）
3. 敵はコンパクトな棒だけ

- 端寄せHUD。中央は3Dに明け渡す。
- 未装備スロットに「NO ACTIVE」を7個並べない（折りたたむ）。
- PAUSE は右上アイコン化。終了はポーズメニュー内のみ（現行の安全設計は維持）。

## 9. ゲート ― 「落ちうる」ことを確認して初めて意味を持つ

新規ゲートは全て、**旧実装を注入すると落ちること**を実演してから採用する。

### 9-1. ⭐ 通信量ゲート（**現状は存在しない。新設する**）

VORTEX の `wireSelftest.ts` は挙動しか見ていない。バイトを測っているのは
`src/arena/net/wireSizeSelftest.ts`（SCRAP CROWN 側）だけである。

- `new TextEncoder().encode(json).byteLength` で測る。
  ⚠ `JSON.stringify().length` は **UTF-16 の文字数**でありバイト数ではない。
- イベント無しの最大 snapshot：**10 KiB 以下**
- 単一イベント：**128 バイト以下**
- 通常50ms窓のイベント込み：**12 KiB 以下**
- プロトコル上限256イベントの安全ケース：**64 KiB 以下**
- コンボ窓・delayed queue による定常増分：**0 バイト**
- baseline を保存し、イベント無し snapshot が理由なく **1% 以上増えたら失敗**

### 9-2. 決定論

同一 seed・build・入力 tick 列で2つの sim を回し、全 snapshot とイベント列を比較。
5アリーナ×2/3/4機で不一致0。窓の境界 `expiresTick-1 / expiresTick / +1` を必ず検査。

### 9-3. 到達性

各新スキルに専用 fixture を用意し、**8本すべてが1回以上成功**、条件不成立時の誤発動0。
12コンボは窓内でちょうど1回、窓外で0回。opener 1回から窓を二度消費できない。
自由対戦での「条件成立後の発動成功率」を **15–80%** に収める。
15%未満は死にスキル、80%超は判断不要の連打。

### 9-4. 一発あたりの効果量（paired run で効果だけ on/off）

- 即時HP減少：対象 `hpMax` の **25%以下**
- 回転差：`launchSpin` の **20%以下**
- 単一デバフ：倍率 **0.6以上**・持続 **4秒以下**
- 新 effect の各指標が既存98スキル同分類の **P95 × 1.15 を超えない**（例外はスキルID単位で明示）

### 9-5. コンボ固有

A / B / A+B / A+B+Combo の4条件を同一 seed 群で比較。
- 勝率上昇は A+B 比で **3–10pt**
- 中央KO時間の短縮は **15%以内**（P95 でも25%以内）
- コンボが一試合の総damage/repair/spin swing の **25%を超えない**
- finisher 成功率 **15–50%**、120秒戦で同一コンボ平均 **0.5–3回**

⭐ 勝率は一指標にすぎない。発動率・KO時間・寄与率を同時に見ないと、
「当たれば試合を決めるが滅多に成立しない」不健全なコンボが勝率50%で通過する。

### 9-6. 性能

4機平均 step **4ms未満**（現行維持）、8機 **12ms未満**、4機P95 **8ms未満**、8機P95 **16ms未満**。
コンボ照合だけの増分は **0.15ms/step 未満かつ baseline比5%未満**。

### §9 受け入れ基準の扱い

§9-5 の4条件比較（勝率+3–10pt等）は**未実施**。コンボ成立の機構・順序・帯域は
ゲートで実証済みだが、バランス寄与の定量は今後の実測課題として残る。
§9-6 の性能は playability floor 方式（perfSelftest）に置換済み — 絶対 ms の
壁時計ゲートはマシン依存で常時赤になる実績があるため（teamSelftest の教訓）。

### v3 で追加された不変条件

- **すり抜けの安全**：独楽のフィルタは `GROUP_ARENA` への OR で構築される。
  アリーナビットを含まないフィルタは**書けない**（world.ts の groups 定義）
- **決着の質**：ガード時間（8s）内の決着ゼロ・接触ダメージ中央値 ≥9 を
  finishSelftest が本番ピッカー（content/cpuBuild — App と単一ソース）で監視
- **コンボの帯域**：窓は RuntimeTop のみに存在し、スナップショットとは
  キー集合・バイト数とも一致（comboSelftest CB5）

### v2 文書の訂正

§冒頭の「1 ring-out : 31 destroyed」は headlessSelftest のナパーム
フィクスチャ（damage 82・半径10m）の産物で、**実プレイの分布ではない**。
本番同等ビルドの実測は場外90%・即決着多発・正規時間内破壊ゼロだった。
数字の出典となるフィクスチャを確認せずに設計判断へ引用しないこと。
